수집한 링크를 다시 찾고 활용하는 지식 아카이브

원문·요약·검색 인덱스의 역할을 나누고, 웹·메신저·CLI에서 들어온 자료를 같은 저장 흐름으로 연결했습니다.

ROLE수집·저장·검색 API 및 사용자 접점 구현
TECHNOLOGYPython · FastAPI · PostgreSQL · pgvector · HTTP · Web Clipper
SOURCE소스 비공개
ON THIS PAGE

01OVERVIEW

무엇을 만들었나

웹 페이지와 영상 링크를 모아 요약·분류·보관하고 다시 찾을 수 있는 개인 지식창고를 만들었습니다. 북마크 UI와 웹 클리퍼에 더해 지식 서비스, Discord와 wf sum 명령으로 수집 접점을 넓혔습니다.

02PROBLEM

어떤 문제가 있었나

링크를 저장해도 원문을 다시 찾고 필요한 근거를 꺼내는 작업이 남았습니다. 생성된 요약, 원문, 임베딩을 같은 정보처럼 다루면 출처를 잃거나 검색 실패를 답변의 확신으로 오해할 수 있습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

원문 추출과 생성형 AI 호출은 실패할 수 있고, 임베딩을 만들 수 없는 환경도 있습니다. 새 지식 서비스의 메모리 저장소와 PostgreSQL 아카이브는 지속성이 다르며 요약 성공과 영구 보관 성공도 따로 확인해야 합니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

원문과 메타데이터를 아카이브에 두고 임베딩을 검색용 데이터로 분리했습니다. 의미 검색이 불가능하면 키워드 검색을 사용하고, 답변에는 검색된 문서를 근거로 연결합니다. 새 요약 서비스는 저장 성공 여부와 아카이브 ID를 응답에 담도록 구성했습니다.

05IMPLEMENTATION

어떤 책임을 구현했나

북마크 등록·수정·폴더·태그·복습·브리핑과 pgvector 검색 및 근거 문서 기반 채팅을 구현했습니다. 이후 웹·영상 수집, 리서치·인사이트 검색, 요약과 아카이브를 연결하는 지식 서비스를 추가했습니다. wf sum은 이 서비스를 호출하며 아카이브 ID가 있는 결과를 터미널에 표시합니다.

06RESULT

무엇이 확인됐나

자료 수집부터 보관·검색·답변까지 이어지는 코드 경로를 확인했습니다. 기존 아카이브의 DB 저장과 새 지식 서비스의 메모리 저장을 구분해 소개합니다. 검색 정확도와 요약 품질은 별도 평가 수치가 없어 성과로 제시하지 않습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

요약이 생성됐다는 사실만으로 보관과 검색 준비가 끝난 것은 아닙니다. 원문 추출 품질, 영구 보관 여부, 임베딩 상태와 검색 근거를 사용자에게 구분해 전달하고 실패 대체 결과도 표시하는 방향으로 발전시켜야 합니다.

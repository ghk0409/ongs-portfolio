05 / FINANCE개인 프로젝트

Weissflow — 가상 투자 원장과 알림 행동의 안전 경계

알림을 곧바로 명령으로 취급하지 않고, 상태 변경과 검증의 책임을 분리했습니다.

ROLE제품·백엔드 아키텍처·구현
TECHNOLOGYTypeScript · NestJS · PostgreSQL · Next.js · Python · Kubernetes
SOURCE소스 비공개
ON THIS PAGE
01 Overview02 Problem03 Constraints04 Architecture / Decision05 Implementation06 Result07 Retrospective
01OVERVIEW

무엇을 만들었나

Weissflow는 금융 데이터 조회, 가상 투자, 모니터링과 자동화 기능을 엮는 개인 프로젝트입니다. 여러 서비스의 기능을 나열하기보다 가상 자산의 상태를 일관되게 바꾸고 알림을 안전한 행동으로 연결하는 경계에 집중했습니다.

02PROBLEM

어떤 문제가 있었나

시장 정보, 분석, 알림과 투자 명령은 서로 다른 속도로 움직입니다. 알림을 곧바로 주문처럼 취급하거나 화면과 백엔드가 각각 잔고를 계산하면 중복 처리와 상태 불일치가 생길 수 있습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

외부 금융 데이터와 도구는 실패하거나 지연될 수 있습니다. 가상 투자와 실제 브로커 연동은 위험 수준이 다르므로 실행 모드를 분리해야 했고, 사용자에게 보이는 알림에는 현재 상태와 허용된 행동이 함께 전달되어야 했습니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

가상 투자 상태 변경은 백엔드의 단일 트랜잭션 경계에 두었습니다. 모니터링은 이벤트를 영속화하고 SSE로 화면에 전달하며, 화면의 행동은 별도 API에서 다시 검증합니다. 시뮬레이션·페이퍼·실거래 모드를 구분하고 실거래 경로에는 잠금과 승인 조건을 둡니다.

  1. 외부 데이터
  2. 모니터링
  3. SSE 피드
  4. 행동 검증
  5. 가상 원장
05IMPLEMENTATION

어떤 책임을 구현했나

NestJS 투자 API의 가상 투자 원장과 배치 리밸런싱, 모니터링 데몬의 피드 저장·행동 페이로드, SSE 피드와 Next.js 전달 경로를 구성했습니다. 정기 실행 작업은 중복 실행을 막는 설정으로 분리했고, 외부 데이터 도구와 핵심 원장 사이의 서비스 경계를 문서화했습니다.

06RESULT

무엇이 확인됐나

최신 저장소 문서와 작업 기록에서 가상 투자, 피드 저장, 스트리밍 전달, 정기 모니터링의 구현 흐름을 확인했습니다. 저장소가 비공개이므로 외부 검토용 코드 링크는 제공하지 않으며, 수익률·응답 속도·정확도는 성과로 주장하지 않습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

금융 기능에서는 자동화했다는 사실보다 어디에서 멈추고 다시 확인하는가가 중요했습니다. 공개 데모를 만든다면 가상 데이터임을 명시하고, 운영 데이터와 실제 투자 기능의 분리를 가장 먼저 검증하겠습니다.

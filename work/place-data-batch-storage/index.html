01OVERVIEW

무엇을 만들었나

위치 기반 서비스의 장소 데이터 저장 경로를 단계적으로 보완했습니다. 전체 항목의 병렬 처리에서 시작해 작업 묶음, 카테고리 일괄 처리, 주소와 기존 장소 조회의 구조를 수정했습니다. 같은 서비스의 순위·큐 후처리와는 다른 데이터 저장 문제입니다.

02PROBLEM

어떤 문제가 있었나

항목별 비동기 저장이 한꺼번에 실행되면서 DB 연결을 사용하는 작업도 함께 늘어나는 구조였습니다. 각 항목의 저장에서 카테고리·주소·기존 장소를 처리하는 반복 조회도 보완 대상이었습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

장소·카테고리·주소를 함께 저장해야 했고, 주소 계층에서는 앞서 저장한 부모 ID를 다음 단계에 전달해야 했습니다. 여러 차례 변경된 경로여서 초기 동시 작업 제한과 후속 일괄 처리 구조를 구분해야 합니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

먼저 지정된 크기의 묶음마다 병렬 처리하고 묶음 사이에서는 기다리도록 변경했습니다. 이후 유즈케이스의 묶음 처리를 일괄 저장 서비스로 대체하고 카테고리를 묶어서 처리했습니다. 주소는 입력별 묶음을 다루되 계층 내부는 순차 저장하고, 기존 장소는 묶음 조회한 결과를 각 저장 단계에 전달하도록 보완했습니다.

05IMPLEMENTATION

어떤 책임을 구현했나

작업 묶음 유틸리티와 유즈케이스 적용, 카테고리 일괄 처리·일괄 저장 경로를 개발했습니다. 주소 묶음 조회·저장 및 부모 ID를 전달하는 계층 내 순차 처리를 추가했습니다. 기존 장소의 항목별 조회를 묶음 조회로 바꾸고 조회 결과를 저장 함수에 전달하도록 수정했습니다.

06RESULT

무엇이 확인됐나

저장 경로를 작업 묶음과 데이터별 일괄 처리로 보완하고, 기존 장소 조회를 반복 호출하지 않도록 조회 결과를 전달하는 구조로 수정했습니다. 초기 제한 방식과 후속 일괄 처리 변경은 각각의 단계로 구분합니다.

07RETROSPECTIVE

무엇을 다시 고려하나

지금 다시 보면 병렬 작업 수 조절과 반복 조회 보완은 서로 다른 접근입니다. 다음에는 각 변경 단계의 연결 수·쿼리·실행 시간을 따로 기록해 구현 변화와 실제 성능 결과를 구분해서 설명하고 싶습니다.

05 / ASYNC WORKFLOW실무 · 업무 알림·문서 생성

Transactional Outbox로 알림과 문서 생성을 분리하기

업무 데이터 저장과 작업 접수는 한 트랜잭션에, 외부 발송과 파일 생성은 독립 워커에 두었습니다.

01OVERVIEW

무엇을 만들었나

가입·인증·계정 변경 알림과 업무 문서 생성을 API 요청 경로에서 분리했습니다. MySQL Outbox를 읽는 독립 asyncio 워커와 이벤트별 핸들러를 구현하고, 업무 원천 데이터를 스냅샷으로 고정해 Excel 파일로 만드는 흐름을 연결했습니다.

02PROBLEM

어떤 문제가 있었나

업무 데이터는 저장됐지만 이메일이나 파일 생성이 실패할 수 있고, 외부 처리 중 DB 잠금을 잡으면 다른 요청도 지연될 수 있었습니다. 재요청과 워커 재시작은 같은 작업의 중복 실행과 결과 덮어쓰기 문제를 만들었습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

기존 MySQL과 Python 환경을 활용하면서 API와 워커를 독립 배포해야 했습니다. 외부 SMTP·스토리지의 동작을 DB 트랜잭션에 포함할 수 없었고, 환경별 처리 분리와 인증 이벤트의 원래 만료 시각을 유지해야 했습니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

별도 큐 인프라를 먼저 늘리기보다 업무 데이터와 Outbox 이벤트를 같은 DB 트랜잭션으로 저장했습니다. 워커는 짧은 claim 트랜잭션을 끝낸 뒤 외부 처리를 수행하고, lease token으로 결과 기록의 소유권을 확인합니다. 문서는 요청 멱등성 키와 원천 스냅샷을 사용합니다.

05IMPLEMENTATION

어떤 책임을 구현했나

이벤트 종류·버전별 라우팅, 환경 필터, 제한된 동시 처리, deadline 검사, 일시적 오류 재시도와 DEAD 처리를 구현했습니다. 문서 작업은 원천 스냅샷·정책 버전·해시를 기록하고 생성·업로드·완료 상태를 구분했습니다. 템플릿 잔존값과 셀·도형 관계 보존 문제도 수정하고 안전 종료와 관측 지표를 보강했습니다.

06RESULT

무엇이 확인됐나

API의 이벤트 접수와 워커의 외부 처리 경계, lease로 보호된 상태 전이, 스냅샷 기반 파일 생성 코드가 구현돼 있습니다. 관련 테스트에는 만료·재시도·오래된 lease·생성 및 저장 실패·템플릿 렌더링의 경계 조건이 포함됩니다. 운영 지연 감소나 exactly-once 처리는 성과로 주장하지 않습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

접수를 원자적으로 만들었다고 외부 부작용까지 원자적이 되는 것은 아니었습니다. 외부 성공과 DB 완료 기록 사이의 실패 구간을 설명해야 했습니다. 재처리 권한, 보존 정책, 중복 발송 대응과 결과 대사를 함께 설계해야 운영 가능한 자동화가 됩니다.

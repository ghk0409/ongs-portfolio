02 / INTEGRATION실무 · 외부 레거시 농장 데이터 연동

레거시 데이터를 신규 서비스에 연결하는 경계 API

외부 스키마를 내부 모델에 직접 노출하지 않도록 변환 경계를 두었습니다.

ROLE연동 API·데이터 변환 설계 및 구현
TECHNOLOGYPython · FastAPI · Oracle · MySQL
SOURCE코드 비공개
ON THIS PAGE
01 Overview02 Problem03 Constraints04 Architecture / Decision05 Implementation06 Result07 Retrospective
01OVERVIEW

무엇을 만들었나

외부 Oracle 기반 시스템의 농장·운영 데이터를 신규 서비스에서 사용할 수 있도록 별도 연동 API를 만들었습니다.

02PROBLEM

어떤 문제가 있었나

외부 시스템의 테이블과 코드 체계가 내부 도메인과 달랐습니다. 신규 서비스가 외부 스키마를 직접 알고 의존하면 공급자 변경, 누락 데이터와 장애가 내부 기능 전체에 전파될 수 있었습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

외부 데이터의 소유권과 갱신 주기는 내부에서 통제할 수 없었습니다. 기존 계약·현장 데이터와 연결할 식별 규칙이 필요했고, 읽기 실패와 값 누락도 정상적인 운영 조건으로 다뤄야 했습니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

외부 스키마를 그대로 전달하지 않고 연동 경계에서 조회·매핑·검증한 뒤 내부 응답 모델로 변환했습니다. 외부 식별자와 내부 식별자를 구분하고, 호출 실패가 내부 데이터의 사실처럼 저장되지 않도록 했습니다.

05IMPLEMENTATION

어떤 책임을 구현했나

Oracle 조회 로직과 변환 규칙을 별도 서비스로 분리했습니다. 필드·코드 매핑, 누락 값 처리, 오류 응답과 호출 경로를 정리하고 신규 플랫폼에서 필요한 데이터만 API로 노출했습니다.

06RESULT

무엇이 확인됐나

신규 서비스가 레거시 DB 구조를 직접 의존하지 않고 필요한 데이터를 사용할 수 있는 접점을 확보했습니다. 처리량이나 장애 감소율은 검증 가능한 공개 자료가 없어 적지 않습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

연동의 핵심은 데이터를 옮기는 속도보다 누가 어떤 값의 원본인지를 분명히 하는 일입니다. 앞으로도 스키마 변경 감지와 매핑 회귀 테스트를 경계의 기본 운영 항목으로 유지해야 합니다.

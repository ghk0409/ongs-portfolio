06 / INTEGRATION SAFETY실무 · 외부 업무 연동

외부 업무 연동을 검증·전송·확인 상태로 나누기

원천 동기화부터 전송 후보와 처리 이력까지 연결하고, 결과가 불명확한 요청은 자동 재전송하지 않도록 했습니다.

01OVERVIEW

무엇을 만들었나

외부 업무 시스템의 현재 상태를 동기화하고 변경 이력을 저장하는 연동 서비스를 확장했습니다. 이어서 기간별 업무 데이터를 전송 후보로 묶고, 검증·보류·전송·결과 확인을 API와 운영 대시보드에서 다루도록 구현했습니다.

02PROBLEM

어떤 문제가 있었나

읽기 연동만 있을 때와 달리 전송은 외부 상태를 바꿉니다. 식별 매핑이나 집계 기간이 틀리면 잘못된 대상에 전송될 수 있고, timeout은 미접수인지 접수 후 응답 유실인지 구분하기 어렵습니다. 원천 그룹이 분리·합병될 때 저장 충돌도 발생할 수 있었습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

외부 스키마·인증·호출 제한과 업무별 날짜 기준을 따르면서 기존 중계 경로를 유지해야 했습니다. 필수 식별자가 누락된 원천, 대량 후보, 중단된 실행과 처리 결과가 미확인인 작업도 정상적인 관리 대상으로 남겨야 했습니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

원천 데이터, 현재 후보와 전송 시점의 스냅샷을 구분했습니다. 검증용 dry-run과 실제 전송을 분리하고 업무 키·내용 해시·상태 전이로 재요청을 판단합니다. 전송 결과 미확인은 확인 대사 전까지 보류하며, DB 저장 재시도와 외부 요청 재시도를 같은 처리로 묶지 않았습니다.

05IMPLEMENTATION

어떤 책임을 구현했나

현재 상태·변경 이력 적재, 원천 식별 매핑, 후보 그룹·누락 사유·보류 관리와 검증 이력을 구현했습니다. 요청 간격과 실행 예산을 제한하고 남은 작업은 보류로 반환합니다. 후보 소유권의 잠금 순서를 정렬하고 월 전체 갱신을 필요한 이전 후보 갱신으로 좁혔으며, deadlock과 잠금 timeout은 해당 저장 트랜잭션만 제한적으로 재시도합니다.

06RESULT

무엇이 확인됐나

직접 작성한 코드에서 검증과 실전송의 분리, 미확인 상태의 자동 재전송 제외, 원천 변경 충돌과 그룹 변경 처리 경계를 확인했습니다. 회귀 테스트에는 그룹 분리·합병, 재시도 rollback, 날짜 기준과 비밀값을 노출하지 않는 준비 점검이 포함됩니다. 외부 실접수나 자동화 가동률은 이번 검토에서 확인하지 않았습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

자동화의 품질은 얼마나 많이 보내는가뿐 아니라 어떤 상태에서 멈추는가에 달려 있었습니다. 검증·설정 준비·외부 접수를 각각 다른 증거로 다뤄야 합니다. 보류 이유, 대사 절차, 재처리 권한과 작업 추적을 운영자가 이해할 수 있는 형태로 유지하는 것이 중요합니다.

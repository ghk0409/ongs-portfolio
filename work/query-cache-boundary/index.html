17 / CACHE & API실무 · 데이터 분석 조회 API

조회 조건과 TTL을 API 캐시 경계에 모으기

응답 캐시 처리를 인터셉터로 구성하고, 조회 조건별 키·TTL과 원시 query 값의 정규화를 경계에서 다뤘습니다.

01OVERVIEW

무엇을 만들었나

데이터 분석 조회 API의 Redis 캐시 레이어와 응답 캐시 인터셉터를 개발했습니다. 조회 조건별 키와 TTL을 구성하고 인터셉터에서 사용하는 query 값의 타입·표현을 보완했습니다.

02PROBLEM

어떤 문제가 있었나

같은 조회 엔드포인트에서도 범주·기간 등의 조건에 따라 결과가 달랐습니다. 캐시 키에 이 조건을 반영해야 했고, 인터셉터가 받는 원시 query 값은 검증·변환 이후의 DTO 값과 구분해서 다뤄야 했습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

캐시 처리는 HTTP 요청 경계에서 실행되고 TTL은 메타데이터로 전달됐습니다. 키 생성 시 요청의 원시 문자열과 전체 범주를 나타내는 값을 함께 처리해야 했습니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

공통 인터셉터에서 캐시 조회·응답 반환·결과 저장을 처리하고, 조회별 하위 인터셉터가 조건에 맞는 키를 구성하도록 나눴습니다. 컨트롤러에는 키와 TTL 데코레이터를 적용했습니다. 원시 query의 숫자형 조건을 해석하고 전체 범주 표현을 정규화했으며 키 조합 순서도 정리했습니다.

05IMPLEMENTATION

어떤 책임을 구현했나

캐시 hit 시 응답을 반환하고 miss 시 조회를 실행한 뒤 TTL과 함께 저장하는 인터셉터를 개발했습니다. 조건별 키 생성과 TTL 데코레이터를 컨트롤러에 적용하고, query 값의 타입 변환·전체 범주 정규화와 키 조합을 수정했습니다. 서비스 내부의 이전 키 생성 코드는 주석 처리해 역할을 정리했습니다.

06RESULT

무엇이 확인됐나

조회 조건과 TTL을 사용하는 응답 캐시 경계를 구현하고, 원시 query 값과 전체 범주를 다루는 키 생성 처리를 보완했습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

지금 다시 보면 캐시 구현은 저장소를 붙이는 것뿐 아니라 어떤 요청을 같은 결과로 취급할지 정하는 일입니다. 다음에는 키 충돌·조건별 결과·만료 동작의 검증과 캐시 사용 지표를 함께 남기고 싶습니다.

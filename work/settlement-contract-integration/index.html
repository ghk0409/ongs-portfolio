01OVERVIEW

무엇을 만들었나

선정산 서비스의 도메인·백엔드를 개발하면서 정산 가능 금액·한도와 요청 기능을 구성했습니다. 계약 관계와 취소 후 재생성 흐름, 외부 서명 화면 연결도 보완했습니다.

02PROBLEM

어떤 문제가 있었나

정산 가능 금액을 구할 때 외부 정산 데이터와 이용 중 금액을 함께 다뤄야 했습니다. 계약 기능에서는 사업자와 계약의 관계, 취소 상태의 기존 계약을 처리하는 흐름도 수정해야 했습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

정산 데이터 조회와 내부 이용 금액, 외부 계약·서명 API를 함께 다뤘습니다. 금융 인터페이스 설계와 실제 외부 통신은 다른 구현 단계이며, 펌뱅킹 부분의 담당 범위는 포트·어댑터 골격 설계입니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

정산 계산·한도·항목을 도메인으로 구성하고 조회·요청을 유즈케이스로 나눴습니다. 이용 중 금액은 저장소에서 조회하도록 연결했습니다. 계약은 사업자와의 관계 및 취소 상태 처리에 맞춰 생성 흐름을 보완하고 서명 화면 요청에 리디렉션 입력을 전달했습니다.

05IMPLEMENTATION

어떤 책임을 구현했나

정산 도메인·유즈케이스·어댑터를 재구성하고 도메인 테스트와 외부 정산 데이터를 모킹한 계산 결과 테스트를 추가했습니다. 사업자–계약 관계 변경, 취소된 계약의 재생성 분기와 서명 화면 연결을 수정했습니다. 펌뱅킹은 포트와 어댑터 골격을 구성했으며 실제 이체 완료 기능으로 소개하지 않습니다.

06RESULT

무엇이 확인됐나

정산 계산·한도와 조회 기능, 관련 테스트 코드를 추가하고 계약 관계·재생성·서명 화면 연결을 보완했습니다. 금융 인터페이스 설계는 별도의 작업 범위로 구분합니다.

07RETROSPECTIVE

무엇을 다시 고려하나

지금 다시 보면 정산 계산, 계약 상태와 외부 연동은 각기 다른 책임입니다. 다음에는 도메인 검증 결과와 외부 통신의 적용 범위를 따로 기록해 인터페이스 설계와 서비스 동작을 명확하게 설명하고 싶습니다.

01 / DOMAIN실무 · 스마트 축산 운영 플랫폼

조직과 현장 리소스를 연결하는 접근 정책

역할만으로 설명할 수 없는 권한을 관계와 리소스 범위로 모델링했습니다.

ROLE백엔드 도메인·API 설계 및 구현
TECHNOLOGYPython · FastAPI · SQLAlchemy · PostgreSQL
SOURCE코드 비공개
ON THIS PAGE
01 Overview02 Problem03 Constraints04 Architecture / Decision05 Implementation06 Result07 Retrospective
01OVERVIEW

무엇을 만들었나

조직, 사용자, 농장과 그 하위 리소스가 얽힌 운영 플랫폼에서 요청자가 어느 범위까지 무엇을 할 수 있는지 일관되게 판단하는 접근 정책을 설계했습니다.

02PROBLEM

어떤 문제가 있었나

단순한 사용자 역할만으로는 계약 관계, 조직 소속, 관리 범위와 리소스 계층을 함께 설명하기 어려웠습니다. 엔드포인트마다 조건을 따로 구현하면 기능이 늘수록 권한 판단이 어긋날 위험이 있었습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

기존 사용자·조직 데이터와 API 동작을 유지해야 했고, 관리자가 다루는 범위와 실제 데이터 조회 범위가 서로 맞아야 했습니다. 새 기능에도 같은 정책을 재사용할 수 있어야 했습니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

역할 이름보다 주체–관계–리소스–행위를 기준으로 정책을 표현했습니다. 상위 리소스에서 결정된 범위가 하위 조회와 명령에 어떻게 적용되는지 명시하고, API에서 같은 정책을 호출하도록 경계를 두었습니다.

  1. 사용자·조직
  2. 관계와 관리 범위
  3. 공통 접근 정책
  4. 조회·변경 API
05IMPLEMENTATION

어떤 책임을 구현했나

조직·사용자 관계와 현장 리소스 모델을 정리하고, 접근 가능한 리소스 집합을 계산하는 서비스와 조회 필터를 연결했습니다. 관리자 기능과 일반 사용자 기능에 같은 기준을 적용하고, 허용·거부 및 경계 사례를 테스트했습니다.

06RESULT

무엇이 확인됐나

권한 판단의 근거가 도메인 모델과 공통 정책에 모여, 새 API가 기존 규칙을 재사용할 수 있는 구조를 마련했습니다. 공개 가능한 운영 지표는 아직 확인되지 않아 성능·효율 수치는 제시하지 않습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

권한은 미들웨어 한 층의 문제가 아니라 조회 범위와 상태 변경까지 관통하는 도메인 규칙이었습니다. 정책을 중앙화하더라도 예외를 숨기지 않고, 관계 변경과 데이터 이관 시나리오를 테스트로 계속 검증해야 합니다.

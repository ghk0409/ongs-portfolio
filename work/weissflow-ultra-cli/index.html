01OVERVIEW

무엇을 만들었나

Ultra CLI(wf)는 Weissflow의 기능을 터미널에서 사용하는 개발자 도구입니다. wf status, bus, lunch, grass, sum, cluster, briefing, motd, wake, config 명령을 통해 일상 정보, 지식 보관과 홈랩 운영을 연결했습니다.

02PROBLEM

어떤 문제가 있었나

개발 중 필요한 상태 정보와 링크 보관 작업이 웹 화면·메신저·운영 도구에 흩어져 있었습니다. 터미널에서 작업을 이어가려면 짧은 명령으로 서비스를 호출하고 읽을 수 있는 결과로 돌려받는 접점이 필요했습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

별도 패키지 설치나 가상환경 전환 없이 Python 환경에서 실행할 수 있어야 했습니다. 서비스마다 응답 시간과 실패 방식이 다르고, 사람이 읽는 터미널과 출력을 다른 도구로 넘기는 환경을 함께 고려해야 했습니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

명령 파싱과 HTTP 호출, 기능별 응답 해석, 출력 포맷을 나눴습니다. CLI에는 서비스의 비즈니스 로직을 복제하지 않고 게이트웨이와 기존 API를 호출하게 했습니다. 통합 상태는 ThreadPoolExecutor로 병렬 취합하며, TTY 감지와 NO_COLOR 설정으로 출력 색상을 제어합니다.

wf / ULTRA CLI가상 출력 예시

$ wf status

WeissFlow / 통합 상태

클러스터   ● 서비스 응답 확인
교통       도착 정보 수신 지연

각 영역의 상태를 따로 표시합니다.

여러 서비스의 응답을 병렬로 모아 한 화면에 보여줍니다.

$ wf sum https://example.com/article

명령을 선택해 표시 예시를 바꿔 보세요. 네트워크 요청이나 실제 작업은 실행하지 않습니다.

05IMPLEMENTATION

어떤 책임을 구현했나

argparse로 명령·별칭·옵션을 구성하고 urllib로 JSON 요청과 응답을 처리했습니다. status는 교통·식단·GitHub 활동·서비스 상태를 함께 조회하고, motd는 한 줄 출력과 별도 호출 제한 시간을 사용합니다. sum은 요약·아카이브 서비스, wake는 원격 부팅 서비스에 위임하며 설정은 로컬 JSON에 저장합니다.

06RESULT

무엇이 확인됐나

최신 코드에서 명령 디스패치, 병렬 수집, API 키 헤더 전달과 출력 경로를 확인했습니다. HTTP 응답과 서비스 호출을 모킹하는 기존 CLI 테스트 10개를 직접 실행해 통과했습니다. 실서비스 응답 속도와 생산성 향상은 측정 성과로 제시하지 않습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

가벼운 설치와 간단한 명령은 장점이지만 네트워크 의존성은 남습니다. 다음 개선은 실패를 스크립트가 판단할 수 있는 종료 코드, 조회·저장 결과의 구분, 설정과 인증정보 관리, 실제 응답과 대체 데이터의 표시를 강화하는 것입니다.

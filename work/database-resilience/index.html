07 / RELIABILITY실무 · 데이터 접근 계층

DB 연결 장애가 동시 요청으로 번지지 않도록

연결 생성·획득·사용·반납의 소유권을 구분하고, 실패한 소켓을 정리하되 정상 공유 자원은 유지했습니다.

ROLEMySQL 풀·ClickHouse 클라이언트 장애 처리 및 관측 보강
TECHNOLOGYPython · asyncio · aiomysql · ClickHouse · Grafana · Loki
SOURCE코드 비공개
ON THIS PAGE
01 Overview02 Problem03 Constraints04 Architecture / Decision05 Implementation06 Result07 Retrospective
01OVERVIEW

무엇을 만들었나

비동기 백엔드에서 MySQL 연결 풀과 ClickHouse HTTP 클라이언트의 연결 장애 처리·자원 회수·관측 기능을 보완했습니다. 정상 요청의 처리 경로를 유지하면서 timeout·취소·동시 요청 상황의 실패 범위를 좁히는 작업입니다.

02PROBLEM

어떤 문제가 있었나

물리 연결 생성이 공통 잠금을 오래 잡으면 정상 연결을 빌리는 요청도 기다릴 수 있었습니다. timeout 소켓을 닫고도 풀 슬롯을 반납하지 않거나, 개별 연결 오류 때문에 건강한 공유 HTTP 세션을 닫으면 다른 요청까지 연쇄 실패할 수 있었습니다.

03CONSTRAINTS

무엇을 바꿀 수 없었나

여러 요청이 같은 풀·클라이언트를 사용했고 기존 트랜잭션과 async 취소 처리를 유지해야 했습니다. 재시도를 늘리는 것만으로는 풀 고갈을 해결할 수 없었고, 재처리가 안전한 읽기와 부작용이 있는 쓰기도 구분해야 했습니다.

04ARCHITECTURE / DECISION

어떤 경계를 선택했나

연결 생성 I/O를 풀의 공통 조건 잠금 밖으로 분리하고 생성 동시성과 전체 제한 시간을 제어했습니다. 획득·쿼리·트랜잭션·정리에 각각 예산을 두며, 프로토콜 상태를 알 수 없는 소켓은 폐기·반납합니다. ClickHouse에서는 개별 연결 실패와 실제로 닫힌 공유 세션을 구분해 정상 자원을 불필요하게 초기화하지 않도록 했습니다.

05IMPLEMENTATION

어떤 책임을 구현했나

풀 상태 지표와 대기·작업 지연의 구조화 로그, 안정성 대시보드를 추가했습니다. 유휴 연결 검증 timeout 후 제한된 예산 안에서 다른 연결을 재획득하도록 하고 닫힌 슬롯을 회수했습니다. ClickHouse 오류 분류와 재시도 경로를 정리하고, 한 쿼리의 복구가 같은 공유 세션의 다른 쿼리를 깨뜨리지 않는 테스트를 보강했습니다.

06RESULT

무엇이 확인됐나

연결 풀 정체 격리, 취소·timeout 시 자원 정리, 검증 실패 후 재획득과 공유 세션 보존의 변경 코드를 확인했습니다. 저장소에는 결정적 fake를 이용한 동시 요청 회귀 테스트, 합성 벤치마크와 DB smoke 검증 도구가 있습니다. 이번 작업에서 운영 부하 테스트를 실행하거나 전후 지연 수치를 성과로 옮기지는 않았습니다.

07RETROSPECTIVE

무엇을 다시 고려하나

timeout을 추가하는 것만으로는 회복되지 않았습니다. 실패한 자원의 소유자와 반납 경로, 공유 객체의 수명이 함께 맞아야 했습니다. 재시도는 남은 예산 안에서 제한하고, 실제 풀 고갈·연결 정체·쿼리 지연을 관측에서 따로 읽을 수 있어야 합니다.
